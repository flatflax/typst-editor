# 交互设计分析（草稿）

> 目的：项目从 Phase 3（M13–M23）的工程验证转向产品化时，先明确产品定位与用户需求，再据此
> 反推当前实现的缺口，以及需要调整方向的部分。这是一份分析与问题清单，不是最终规格。参考：
> [plan.md](../plan.md)、[architecture.md](architecture.md)、
> [design-principles.md](design-principles.md)、[phase3-single-view.md](phase3-single-view.md)。

## 1. 产品定位（5W1H）

- **谁（Who）**：调研和实测下来，目标用户是已经会 Typst 语法、只是希望日常正文录入更快的
  进阶用户——这是目前能找到真实证据支撑的群体（见 §4）。"完全拒绝语法"这类诉求目前没有
  找到自发的真实证据，不作为产品的首要目标。
- **为什么（Why）**：现有工具都有明显缺口。Word 在长文档、CJK、公式排版上不够稳定；
  Markdown 和 Notion 好写，却没有页面/版式的概念，排版效果完全取决于渲染器，导不出可以
  直接提交或发布的 PDF。LaTeX 和 Typst 排版能力强，但都是源码加预览分栏的心智模型，编辑
  时看到的和最终编译结果之间总有落差——这才是没被满足的需求，不是"要写语法"本身
  （Typst 相较 LaTeX 已经大幅降低了语法门槛），详见 §4。
- **做什么事（What）**：撰写、编辑、排版并导出可提交、可发布的文档，以论文、技术报告、
  双语/CJK 内容、简历为主。这些场景都需要真实分页、一致的样式、公式和引用等学术/技术写作
  要素。
- **什么情境（When/Where）**：正式写作场景，通常是几周内反复编辑的长过程，而不是一次性的
  小改动；使用环境是桌面、专注写作。
- **怎么做（How）**：单一可视化界面直接编辑，背后始终是真实的 Typst 编译，不是近似渲染。
  语法默认呈现方式是"聚焦才可见"——光标离开的内容渲染成排版结果，光标所在的块显示真实
  源码，两者是同一份内容的两种呈现，不是"藏起来的高级功能"和"默认功能"的关系，详见 §6。

## 2. 用户定位

| Persona | 核心诉求 | 对本项目的价值 |
|---|---|---|
| **学术写作者**（研究生/科研人员） | 需要公式、引用、参考文献、交叉引用、图表 | 排版要求高的场景，也是当前内容模型缺口大的场景（见 §5A） |
| **双语/CJK 技术写作者** | 中英文混排质量、样式一致 | 项目对 IME[^ime] 的既有投入天然对齐这个人群；但中英文混排的"样式一致"诉求，实测下来真实痛点集中在 Typst 引擎/模板层面（字体切换、标点挤压、首行缩进），不是编辑器交互层面能解决的，见 §4B、§5C |
| **现有 Typst 用户** | 日常录入希望更快，精细排版时仍要"下潜"到源码 | 目前有真实同类产品实证的人群（Underleaf、TyX、Typstudio[^typstudio]、Katvan 都是做给这个人群的），是近期应该优先服务的对象，见 §4B |

三者的共同点，是都需要"专业排版结果"。产品不默认零语法，默认呈现方式是渲染结果，但语法
始终触手可及——聚焦到内容就能看到、编辑源码，不需要在"零语法"和"进阶下潜"之间做二选一
的产品决策。

## 3. 用户需求分析

| 痛点（现有工具） | 需求 |
|---|---|
| Word：长文档/CJK/公式排版不稳定，样式容易崩坏 | 一致、可靠的排版引擎，不需要靠导出才能确认效果 |
| LaTeX/Typst 源码：源码和最终结果之间总有落差，不是"要写语法"本身 | 编辑时看到的就该是真实结果，不用等导出才知道效果（见 §4） |
| Markdown/Notion：没有页面/版式概念，样式取决于渲染器，排版不可控 | 保留所见即所得，同时用真实排版引擎保证可控、一致的出版级样式 |
| 现成 Typst 生态（模板、包）：质量高，但入口是源码 | 能直接导入、沿用已有的 Typst 文档和模板，且尽可能可视化编辑 |

## 4. 差异化竞争力

| 对比对象 | 排版能力 | 学习门槛 | 编辑心智模型 | 与本项目的差距 |
|---|---|---|---|---|
| Word | 弱（长文档/CJK/公式不稳定） | 低 | 所见即所得 | 用真实排版引擎替代近似渲染 |
| Notion/Typora | 弱（无版式概念，渲染不可控） | 低 | 所见即所得 | 保留同等编辑体验，排版交给真实引擎决定 |
| LaTeX（Overleaf/VS Code） | 强 | 高（需写语法） | 源码 + 预览分离 | 预览已经是真实编译结果，没有近似渲染问题；差距在于要在源码面板和预览面板之间来回切换，本项目把两者合成一个界面 |
| typst.app / VS Code + tinymist / Typstudio[^typstudio]（已停止维护） | 强（真实 Typst 编译） | 高（需写 Typst 语法） | 源码 + 预览分离 | 同上 |
| **Underleaf** | 强（宣称用真实 Typst 编译） | 低（可视化编辑，隐藏语法） | 可视化编辑 / 源码切换 | **实测发现：编辑区是近似渲染，和导出 PDF 有实质差异；结构化编辑待完善；把 Markdown 的部分语义错误地套用到 Typst 上。本项目期望是"编辑时和真实编译之间没有第二套引擎、没有落差"，见 §4B** |

Typora 已经证明"语法所见即所得"是可行的[^typora]，Typst 官方的网页编辑器 typst.app 至今
仍然是源码加预览的分栏形式[^typstapp]。但市面上已经出现了不止一个"可视化编辑 Typst、
背后跑真实编译器"的尝试，Underleaf[^underleaf]、TyX[^tyx] 都是这个方向，说明该方向存在既有成熟产品。

点击 PDF 跳回源码、或反过来从光标位置定位到 PDF，这类双向同步在 LaTeX 生态里也已经是标配
功能，即 SyncTeX[^synctex]。这说明本项目的点击/光标同步机制（M1/M5/M20）是这个品类本该具备的基本能力。

从这张表能看出，"真实编译结果"和"单一界面（不需要分栏切换）"其实是两条不同的轴：LaTeX/
Overleaf、typst.app/tinymist/Typstudio 已经做到了前者，代价是要在两个面板之间来回切换
对照源码和结果；Word、Notion、Underleaf 这类可视化编辑器做到了后者，代价是编辑区本身是
另一套引擎的近似渲染，和真实结果之间有落差。本项目的壁垒，是同时做到这两条：**编辑时看到
的就是真实编译结果本身，因为不存在第二套排版引擎在猜测排版效果，而且不需要在两个面板之间
切换**。M20 到 M23 验证过的机制——把光标直接画在真实的 Typst 渲染结果上——正是这个壁垒
的技术基础，值得继续投入。这个壁垒是否真的是用户在意的东西，目前只有
间接证据（Word"所见非所得"是经典抱怨），还没有一手用户验证，是本文档目前一个尚未闭环
的风险，见 §10。

### 4A. 非文档类产品的可参考交互理念

- **TeXmacs**：理念上与本项目相近的先例——用真实的科学排版引擎渲染文档，编辑操作直接作用
  在渲染结果上，不显示任何标记语言。对矩阵、公式这类结构化内容，它还提供专门的"结构化编辑
  操作"，比如一键给矩阵加一行，而不要求用户手写语法[^texmacs]。但 TeXmacs 也留下一个值得
  警惕的教训：WYSIWYG[^wysiwyg] 把结构隐藏起来之后，用户很容易在公式外面误敲了本该属于
  公式内部的符号，因为两者视觉上看不出区别。本项目设计公式、引用这类新的内容原语时，需要
  考虑加上显式的视觉边界，不能完全依赖"看起来像什么就是什么"。"聚焦即显源码"这个机制
  （见 §6）天然带有这条视觉边界——聚焦态本身就应该用等宽字体、区别于正文的底色，明确
  提示"现在看到的是源码，不是排版结果"。
- **Projectional editing**（以 JetBrains MPS 为代表）：这类编辑器直接持久化并编辑抽象语法
  树，省去"文本转模型、模型再转回文本"这一趟往返，理论上能从根本上避免本项目"编辑必须经过
  parse → transform → serialize、再整文档重编译"这条路径的代价。但 MPS 自己的经验是，这种
  能力是用真实的可用性代价换来的：结构化编辑用在自由行文的正文上，很难让人感觉像是在打字，
  只有专门为表格、图表这类结构化内容设计时才顺畅[^projectional]。这和本项目在 M13、M15 里
  已经摸索出的方向是一致的——表格这类结构化内容走 ProseMirror 的按需 transform，可以理解成
  一种局部、受限的"投影式"编辑，正文仍然是纯文本流。
- **Monaco / VS Code**：它把"文本输入"和"语言服务器这类重量级异步计算"彻底解耦——打字本身
  永远走本地、同步、即时的路径，语言服务给出的诊断、补全等反馈，则作为稍后到达的异步图层
  叠加上去，从不阻塞输入本身[^monaco]。这是"输入延迟"和"权威结果延迟"应该分开设计的一个
  清晰参照，详见 §5D。"聚焦即显源码"机制正是这条原则的直接落地：聚焦态内的输入完全走浏览器
  原生路径，跟 Typst 编译毫无关系，见 §6。
- **Google Docs**：它的分页计算是异步进行的，不会阻塞编辑——先画出页面边界，精细的排版结果
  在背后慢慢补齐[^gdocs-pagination]。这为 §5C 提到的"长文档编译延迟"这个 POC 方向，提供了
  一个具体可以参照的架构范式。

### 4B. 同类产品的参考

- **Underleaf**[^underleaf]：一个已上线、宣称"50,000+ academics"在用的产品——这个数字是
  整条产品线的数据（还包括 AI 写作辅助、引文生成器、LaTeX↔Typst 转换器等），这里只讨论
  它的可视化编辑器本身。它的架构是"富文本编辑区（近似渲染）→ 转成 Typst 源码 → 需要时
  单独跑真实编译器出预览/导出"。实测观察到三点：

  - 编辑区效果和导出 PDF 有实质差异——这正是本项目 M15 验证过的"两套独立布局引擎各管
    一段"模型会遇到的问题；
  - write 模式下列表项暂时无法通过"+"添加，这部分的结构化编辑还不完整；
  - 行首 `# ` 会被渲染成一级标题——这是把 Markdown 的语义套用到了 Typst 上（Typst 的
    标题符号是 `=`，`#` 是代码模式引导符，两者语义不同），用户想输入 Typst 的函数调用
    （`#figure(...)`、`#set text(...)`）时，这条规则会让内容出错。

  这类问题印证了本项目 architecture.md 里拒绝用 Milkdown 的判断（"markdown-first 的解析/
  序列化器会和第二套 Typst 源码格式打架"），也呼应 M6 修复 CodeMirror `closeBrackets()`
  的经验：通用富文本/编辑器组件自带行为，需要针对 Typst 实际语法重新校验。
- **TyX**[^tyx]：定位是仿 LyX 的 Typst 可视化编辑器，但项目自己承认还在早期阶段（"breaking changes are introduced frequently"）。目前相对成型的能力是用 MathLive 做公式可视化编辑（公式本身暂时还是 LaTeX 语法，不是 Typst 原生），Typst 语法导入待完善，通用文档的可视化编辑部分待完善。公式部分可留作参考。（呼应 §5C 的 MathLive 方向）。
- **Typst 论坛上一个 WYSIWYG word processor 展示帖**[^remo-forum]：作者是为了帮同事摆脱
  源码而做的，社区反应正面（"令人印象深刻"，"让人想起 Typora 处理 Markdown 的方式"），但作者
  自己也承认"Typst 支持很广泛的编程语言特性，用纯 WYSIWYG 的方式呈现这些特性，可能很棘手
  甚至不可能"——这句话跟本项目 design-principles.md 规则 2 的判断几乎一致，是一个独立团队
  踩过坑之后得出的印证，不是新的风险。

Typst 官方仓库也有一条关于"是否需要 GUI"的讨论[^typst-gui-discussion]，双方声音都有：公式
输入体验、非程序员写作被打断、双屏需求是真实抱怨；但也有工程师直接反对"GUI 更好"这个前提，
理由是"可编程性会被牺牲"、"有 GUI 不等于体验好"（举了 Vivado/Quartus 的反例）。这条讨论
里反复出现、跨语言（英文讨论、知乎问答）都一致的诉求，是**公式输入体验**，不是"整篇文档
零语法"——如果之后要重新考虑把公式排上日程，MathLive 式的局部可视化编辑[^mathlive]仍然是
值得参照的方向，跟"聚焦即显源码"这个机制并不冲突（公式失焦时可以渲染成 MathLive 式的
可视化呈现，聚焦时退回源码文本，这是同一个通用机制在公式这个具体类型上的应用）。

**跨技能协作**这个痛点确实真实存在——知乎上"导师/合著者不会 LaTeX 怎么办"这类问题，标准
答案是用 Overleaf，它专门做了 Rich Text 模式服务这个场景[^overleaf-richtext]。但这已经是一
个被接受、够用的答案，不需要抛弃源码；本项目 §7 已经明确排除协作编辑，这条痛点目前不在
覆盖范围内，不需要因此改变范围决策，只是要清楚这条痛点是真实的，不是虚构出来的。

**CJK 混排**这条痛点，中文社区（知乎）的实测吐槽高度集中在字体切换、首行缩进、标点挤压这类
Typst 引擎/模板层面的问题，社区靠 zh-kit、elegant-paper 这类模板包解决，不是靠可视化编辑器；
Typst 官方仓库一条至今未关闭的 issue 也印证这是已知的引擎级缺口[^typst-cjk-issue]。Katvan
这个真实项目的解法也不是可视化编辑，而是把双向文本/CJK 相关的代码编辑器体验做好[^katvan]——
三条证据方向一致：CJK 痛点的解法在引擎/模板层，不在"要不要 WYSIWYG"这层，跟 §5A/§5C 的
判断一致。

## 5. 从定位反推：产品化缺口与需要调整的方向

### 5A. 内容模型缺口（比交互体验更基础）

当前的 schema（`model/schema.ts`）缺少公式、引用、参考文献和交叉引用。对照 §2 里的学术写作者画像，这几项应优先于 UI 打磨：

- **数学公式**：公式是 Typst 对 STEM 写作的核心卖点，当前项目的内容模型里完全不存在。跨
  语言调研里反复出现的诉求也正是这一项（见 §4B）。
- **引用、参考文献与交叉引用**：学术写作的刚需，目前也完全没有。引用属于
  design-principles.md 规则 2 里说的"间接产生的渲染内容"：不能直接编辑，只能通过选择或
  跳转来交互。
- **脚注**：M14A 已经证明可以在渲染层定位脚注对应的 fragment，但 schema 和编辑面都还没有
  对应的节点，也就没有编辑入口。
- **模板与起始文档**：目前应用一启动就是一份写死的 demo 文档，没有模板画廊。

这几项之前被排到 v0.1 之后，主要理由是"每种新内容类型都要单独设计 schema 和交互，成本高"。
这个理由在"聚焦即显源码"这套机制下（见 §6）部分不再成立，但**不能一概而论**——"没有排版
geometry 的构造"这个桶里，其实混着三类性质完全不同的东西，需要分开处理：

1. **有语义影响、但没有落脚点的指令**（`#set`、`#let`、`#import`）：`#let color = red` 可能
   被引用几十次，`#set text(font: ...)` 会影响它之后所有正文的渲染——这不是"聚焦看一眼源码
   就够了"的孤立内容，而是一条**引用链**，缺的是"从使用端跳到定义端""从定义端看到影响范围"
   这类导航交互。这跟标签/交叉引用（`<fig:foo>` / `@fig:foo`）是同构问题——都是"一个定义/
   目标 + 若干引用点，需要双向导航"，应该和 §5C 已经在规划的"可引用对象索引 + 选择器 UI"
   （citation picker 那一类）共用同一个 primitive，不是分开设计。
2. **纯粹的人类可读内容、编译器完全无感的东西**（注释 `//`、`/* */`）：这不是"要不要做可视化
   编辑"的问题，是**正确性要求**——注释对编译器而言不参与语义，任何"重新解析、按结果拆分/
   合并块"这类动作（见 §6"新块的产生"）都存在把它悄悄弄丢的风险，尤其是块被拆分或合并时，
   注释该归到哪个新块里，如果交互设计上没有明确"注释必须原样保留、不能被当成可丢弃噪音"这条
   要求，实现出来就可能丢内容。这里只提出这条交互/产品层面的正确性要求；具体靠哪个既有
   primitive 落地、现状是否已经存在遗漏，属于实现阶段要核实的事，不属于交互设计要回答的问题。
3. **值得投入可视化编辑的高频类型**（公式）：这才是前面提到的"聚焦兜底就够，公式除外"，见 §4B。

**这意味着 §7/§8 里"学术写作能力长期要做但不排期"这个决策值得重新评估**——不是因为需求
变了，是因为实现它的成本被这个机制变化大幅降低了（但引用链导航和注释保真这两块工作量不能
被低估），具体要不要提前排期，留待 §10 决定。

### 5B. 编辑体验缺口

- **阻断级**：撤销/重做（Live cursor 视图目前完全没有）、IME 实时组合预览缺失（对 CJK 这
  个定位来说是核心能力，不是锦上添花）、键盘快捷键缺失（当前只能靠按钮操作）。"聚焦即显
  源码"机制下（见 §6），聚焦态内的 IME 组合预览和撤销/重做可以直接复用浏览器原生能力，
  不需要从零造一套。
- **打磨级**：四个并列的视图 tab 应该收敛成一个编辑面。有了"聚焦即显源码"这个具体机制之后
  （见 §6），WYSIWYG tab 和 Typst 源码 tab 的功能会被这个机制直接吸收进 Live cursor 视图，
  不需要"逐个隐藏"这种迂回做法，这两个 tab 可以停止追加新功能，等机制验证完直接退场。表格
  这类结构化编辑从按钮式改成 hover 出现把手、拖拽调整这类现代编辑器的交互，以及 WYSIWYG
  视图下的浮动工具栏打磨——这些都是建立在"两套独立布局引擎"这个已经被 M15 证伪的模型上的
  表面功夫，在新机制验证之前不建议继续投入，很可能需要重新设计。斜杠命令菜单需要补齐（M23
  计划中），可以参照 Notion 验证过的"渐进式呈现"[^slashcmd]；编译诊断应该内联到文档里对应
  的位置；长文档还需要大纲/目录导航。
- **已确定**：保存模型采用自动保存，同时保留用户手动保存的操作，两者并存（见 §7）。
- **剪贴板**：跨块选区的剪切有了具体机制（见 §6）——剪切一段跨块内容，本质就是把这段
  Typst 字节范围的源码文本放进系统剪贴板，再对文档源码做一次结构化删除。这已经足够支撑
  "至少能拿到源码文本"这个最低限度的产品决策，已经在 §7 确认为 v0.1 范围内。

### 5C. 需要重新 POC[^poc] 验证的方向（不受此前结论束缚）

- **渲染层的原生文本能力与无障碍访问**：Typst 官方文档说明，`typst-svg` 把每个字形转成
  路径，SVG 里的"文字"天生没法被浏览器原生选中、复制或读屏[^typst-svg-a11y]。这个选择带来
  的后果——没有原生复制/粘贴、没有屏幕阅读器、没有浏览器原生页内查找、撤销/重做只能自己
  造一套历史栈、光标移动要经过到 Rust 的异步往返——可以参照 PDF.js 的 Text Layer 方案，
  补一层不可见 DOM 文本来解决[^pdfjs-textlayer]。"聚焦即显源码"机制下（见 §6），这些问题
  的范围大幅收窄：只要光标停在某个块内（绝大多数编辑时间），这个块就是一段原生可编辑
  文本，复制/粘贴/撤销/屏幕阅读/输入法全部原生免费；Text Layer 这类补丁方案只需要覆盖
  "当前没有任何块处于聚焦态、且存在一段跨块选区"这一种少数场景，不再是全局性的架构缺口，
  优先级可以下调。
- **长文档编译延迟**：M14、M16 已经验证过，"整文档编译层"的线性代价很难规避，M21 也已经
  接受"长文档打字会变卡"作为 v1 的限制。"聚焦即显源码"机制下（见 §6），打字本身发生在
  原生文本框里，和 Typst 编译完全解耦，只有失焦/提交时才触发编译——"打字变卡"这个急性症状
  大概率会随这个机制自然消失，剩下的只是"提交超长文档的那一下编译还是慢"这个温和很多的
  版本。长文档编译延迟不必再作为独立专项去单独攻克，先等 §10 的 Spike 验证完再看是否还有
  必要。
- **公式的编辑交互**：MathLive 已经证明公式可以做到可视化编辑，同时和类 LaTeX 源码双向
  同步[^mathlive]。跨语言调研反复印证这是一致出现的真实诉求（见 §4B），且和"聚焦即显源码"
  机制天然兼容——公式失焦时渲染成 MathLive 式可视化呈现，聚焦时退回源码文本。
- **引用与交叉引用的交互原语**：需要一个"文档内可引用对象的索引 + 选择器 UI"。Overleaf 的
  Insert Citation、Google Docs 的 Cross Reference 都是成熟参照[^citepicker]。这个 primitive
  应该和 §5A 里 `#set`/`#let`/标签的引用链导航需求共用同一套索引和跳转机制，不是分开
  设计——两者都是"一个定义/目标 + 若干引用点，需要双向导航"这个同构问题。

### 5D. 编辑器交互流畅性

当前架构里其实有三条独立的延迟，被同一条链路耦合在一起：

1. **光标/选区移动延迟**：点击定位、Up/Down、拖拽选区，每一次都要走一趟 `invoke` 往返（M20）。
2. **打字到重绘延迟**：keystroke → splice source → 整文档重编译 → 重绘，耗时随文档长度
   线性增长（M21/M14）。
3. **权威结果到达前的反馈**：M22 的悬浮徽标，只覆盖了第 2 条里的等待窗口。

Monaco 的原则（见 §4A）说明，这三条不该被当成同一个问题：输入路径的延迟任何时候都不应该
让人感觉到迟滞；权威渲染的延迟可以慢，但必须诚实地反馈进度。

"聚焦即显源码"机制（见 §6）对第 1 条的影响比预期更大：**一个收起的（非选区）光标永远只会
落在某一个块内**，只要光标是点状的，就应该直接进入那个块的聚焦/原生态，移动交给浏览器
原生处理，不需要经过 Rust。自绘几何机制（M20）还需要负责的，只剩"跨块选区的静态
高亮范围怎么画"——这是一个更简单、更低频的问题（画几个矩形，不需要维护一个逐字符移动、
还要闪烁的动态光标）。也就是说，"光标每次移动都要经过一次到 Rust 的异步往返"这条架构性
延迟下限，很可能大部分场景根本不需要真的解决，因为触发这个路径的场景本身在新机制下大幅
减少了。这个判断还没有实测验证，是 §10 里第二优先级的 Spike[^spike]。

## 6. 核心交互机制：聚焦即显源码

聚焦即显源码取代"零语法"，成为编辑体验的核心机制。规则：

**聚焦态 vs 失焦态**：光标/选区完全落在某一个块（目前定粒度为整段/整块，参照 Typora，不做
inline 级别的精细 reveal，那个留后续打磨）内时，这个块整体退化成一个原生的、可自由增高的
文本编辑区（textarea/contenteditable），内容是这个块对应的原始 Typst 源码；光标/选区移出
这个块的范围后（含窗口/App 失焦），这个块的当前文本内容被重新解析、拼回文档树，视觉上切回
渲染态——有排版 geometry 的部分渲染成墨迹，没有 geometry 的部分显示占位符。这个占位符只是
"失焦时显示什么"这一层的默认处理；`#set`/`#let`/标签这类有语义影响的构造，占位符之外还需要
引用链导航交互，注释这类构造还需要保真保证，不能止于占位符，具体分类见 §5A。聚焦态应有明显
区别于正文的视觉样式（等宽字体、浅色底），提示"现在看到的是源码"（呼应 §4A TeXmacs 的教训）。

**块内编辑 vs 结构化编辑，分工不变**：这个机制解决的是"一个块内部的文本内容怎么编辑"，不
替代已有的结构化编辑 primitive（design-principles.md 规则 1）——插入新块、调整表格行列、
调整列表层级，依然走 parse → transform → serialize 这条路。

**新块的产生**：Typst 源码里空行分隔段落，因此"聚焦态里打出一个空行"天然对应"应该拆成
两个块"。两种粒度可选：

- **懒惰版（先做这个）**：聚焦态里可以自由输入任意内容（包括空行、整段粘贴），不做实时
  拆分，失焦那一刻才把当前文本整体重新解析，按解析出的块数量原地拼接（1 个变多个是新增，
  清空到 0 个是删除）。
- **抢跑版（后续打磨）**：识别到完整的空行分隔时，立刻用语法解析（`parse_typst_ast`，不
  是全量 `compile_typst`，成本低）把已完成的部分拆出去、拼进文档树、复用 M22 已有的乐观
  pending 视觉（先显示未确认状态，真实编译跟上后再换成真实渲染），光标留在新的、还聚焦着
  的剩余部分继续输入。
- 需要先对着 `typst-syntax` 的实际 parser 核实：空行分段规则是否在列表项内部、表格单元格
  内部也同样成立，不能凭对 Markdown/LaTeX 的印象假设。

**跨块选区与剪切——两套体系并存**：单块内是原生文本框行为（原生光标、选区、IME、撤销）；
跨块是已有的 M20 机制（自绘选区画在真实几何上，Typst 字节偏移寻址）。切换只在"选区跨出块
边界"这一刻发生：立刻提交当前块（语法解析、拼回文档树）、用这次解析结果精确换算字节偏移
（不是近似映射，因为解析和偏移换算用的是同一份刚生成的数据）、把控制权交给跨块选区机制。
一次连续的拖拽/shift 选择手势里，当前处于单块模式还是跨块模式只在手势结束时重新判定一次，
不中途来回切换。剪切在跨块模式下，是"复制这段字节范围的源码文本到剪贴板 + 对文档源码做一次
删除 transform"，不是任何文本框的操作。

**提交失败的兜底**：块内文本解析不出合法 Typst 语法时（比如打到一半的未闭合函数调用），
不能崩、不能丢内容——复用已有的"逐字透传"primitive（`unsupported_block`/`typst_call`）。

这个机制生效后，design-principles.md 规则 2 可以考虑简化：现在的版本是"有 geometry→直接
编辑 / 间接产生→inspector 查看"，基础的显示规则可以合并成一条——"聚焦→源码文本，失焦→按
geometry 决定怎么渲染"，不需要维护两套不同的心智模型。但这条简化只覆盖"这个块的内容长什么样"
这一层，不能覆盖 §5A 提出的另外两条要求：`#set`/`#let`/标签这类构造，失焦时除了占位符，还
需要引用链导航交互（见 §5A、§5C）；注释这类构造，无论聚焦与否都必须原样保真，不能只满足于
"有没有地方显示它"。这个简化建议还没有正式改写 design-principles.md，留到 §10 的 Spike
验证完再定稿。

## 7. v0.1 范围决策（2026-09-09 确认）

- **学术写作能力**（公式、引用与参考文献）：长期需要覆盖。原判断"不在 v0.1 范围"的理由
  （实现成本高）因为"聚焦即显源码"机制被削弱，具体要不要提前排期，留待 §10 决定。
- **模板体系**（论文、简历、报告的模板画廊）：不在 v0.1 范围内。
- **保存模型**：提供自动保存，同时保留用户手动保存的操作，两者并存。
- **协作编辑**：明确排除，不做。
- **AI 能力接入**：短期内不需要，明确排除。
- **剪贴板最低限度**：至少能复制/剪切出源码文本，机制见 §6，确认为 v0.1 范围内。

待定，还没想清楚：

- 是否保留"查看/编辑 Typst 源码"作为面向进阶用户的独立入口？"聚焦即显源码"机制让这个
  问题的答案更明确——源码入口不再需要是一个独立视图，而是内嵌在同一个编辑面里；具体形式
  （要不要额外保留一个纯只读的全文源码浏览模式）仍然留到后续讨论。

### 冲突判断原则

遇到不在表里的新冲突，按这几条原则判断：

1. **正确性优先于速度**：不能为了让长文档编译更快，就牺牲排版精度或退回近似渲染。性能
   问题要用架构手段解决，不能用"降低真实度"解决。
2. **不能为了新功能牺牲已有功能的正确性**：比如不能为了做出 hover 把手交互，让撤销/重做
   变得更难实现。
3. **简陋方案要留升级路径**：P1 允许先上线简陋版本，但实现时要考虑清楚后续怎么升级，不能
   让简陋方案变成没法迭代的死胡同。
4. **判断依据是用户能不能感知，不是工程量大小**：判断一个功能是不是"必须有"，标准是"缺了
   它，§2 里的目标用户会不会觉得这根本不是一个能用的产品"，不是"这个功能技术上好不好做"。
5. **"零渲染漂移"这条核心壁垒目前只有间接证据，不是已验证的用户诉求**——在 §10 的一手
   用户验证完成之前，任何以此为理由拒绝更简单方案（比如近似渲染+导出前预览）的决策，都要
   明确标注"这是一个还没验证过的假设"，不能当成已确认的事实来使用。

## 9. 现状盘点（供参考）

当前 `App.tsx` 提供四个平级的 tab：WYSIWYG、Typst 源码、Markdown 源码和 Live cursor。这是
工程验证阶段为了并行开发、互相校验才留下的脚手架，不是产品应该有的导航模型。随着"聚焦即
显源码"机制的引入（见 §6），WYSIWYG 和 Typst 源码这两个 tab 的功能会被 Live cursor 视图
直接吸收，不再需要单独维护——下表里对它们的持续打磨投入，按 §5B/§8 的判断应该暂停。逐项
能力覆盖如下：

| 能力 | WYSIWYG 视图 | Live cursor 视图（未来主视图） |
|---|---|---|
| 光标/选区 | ProseMirror 原生 | 自绘，画在 Typst 渲染几何上（M20），预计范围会收窄为仅跨块选区（见 §5D） |
| 键入与 IME | ProseMirror 原生（含实时组合预览） | 隐藏 `<textarea>` 捕获，提交即整文档重编译（M21）；组合过程中无实时预览，"聚焦即显源码"机制落地后可原生获得（见 §6） |
| 撤销/重做 | 依赖 PM 历史（不完整） | 完全没有（M21 记录为未解决），同样可望随新机制原生获得 |
| 持久工具栏 | 有 | 有（M23 slice 1，仅按钮，无键盘映射） |
| 选中态浮动工具栏 | 有 | 无 |
| 斜杠命令菜单 | 有 | 无（M23 后续 slice 计划中） |
| 表格行列操作 | 按钮式 | 同左（M23 原样迁移） |
| 输入延迟反馈 | 无需要 | 悬浮徽标显示原始 source 文本，重编译完成即消失（M22） |
| 诊断/报错 | 预览区上方的纯文本列表 | 同左 |
| 长文档性能 | 不适用 | 编译耗时随页数线性增长，长文档打字有可感知卡顿（M14，见 §5C），预计随新机制自然缓解，待验证 |

## 10. 结论与下一步

### 已确定

1. "零语法"作为核心主张——砍掉。
2. "零渲染漂移"确立为核心差异化，M14A/M20-M23 机制继续保留投入。
3. CJK 排版细节（字体、标点、缩进）是 Typst 引擎/模板层面的缺口，编辑器交互解决不了。
4. "聚焦即显源码"确立为核心编辑机制，粒度定为整段/整块。
5. 该机制不替代结构化编辑 primitive，两者分工明确（§6）。
6. 跨块选区/剪切走双体系并存模型，切换时机绑定在选区跨出块边界那一刻（§6）。
7. 提交失败兜底走已有的逐字透传 primitive。
8. Underleaf 等同类产品的经验说明，语义和结构化编辑是长期迭代投入方向。
9. "没有 geometry 的构造"不能一概而论，拆成三类分别处理（§5A）：`#set`/`#let`/标签这类
   需要引用链导航交互；注释这类需要原样保真的正确性保证；公式这类才是原来说的"值得做可视化
   编辑"。前两类不是"聚焦显源码就够"的简单兜底。
10. **Spike 1 已完成，结论正面**：聚焦→原生 textarea 显源码、失焦→提交并真实重新编译，
    这个核心来回本身观感是对的。过程中发现并修掉三个问题，详见
    [phase4-product-validation.md](phase4-product-validation.md) 的 Milestones：聚焦态的
    宽度必须显式对齐渲染态实际占用的宽度（不能靠 `width:100%`，渲染态本身不会撑满整个可用
    列）；聚焦时不能全选原文（否则下一次按键，包括回车，会整体替换而不是追加，读起来像是
    丢内容）；Esc 不应该有"丢弃草稿"这种和其他退出方式（点击别处、Tab）不一致的特殊语义。
    这三条不是"单段落"这个 spike 范围独有的，Spike 2/3 和后续正式实现都要带上。

### 待确定

| 问题 | 类型 |
|---|---|
| 跨块选区边界切换会不会卡/闪 | 技术验证（Spike 2，风险较集中） |
| 失焦才拆分 vs 打空行就抢跑剥离，哪个手感更好 | 技术验证（Spike 3） |
| Typst 空行分段规则在列表项/表格单元格内是否也成立 | 事实核查 |
| 公式、引用要不要因为实现成本降低而提前排期 | 产品决策 |
| 是否保留独立的"查看/编辑源码"入口 | 产品决策 |
| "零渲染漂移"用户到底在不在乎，还是能忍受"近似渲染+导出前检查一眼" | 用户验证 |
| 引用链导航（`#set`/`#let`/标签）和 citation picker 共用的索引/跳转 primitive，具体交互形式怎么设计 | 交互设计（§5A、§5C） |

### 暂停投入

1. 四个 tab 渐进收敛路径——被"聚焦即显源码"机制直接吸收，不再需要单独规划。
2. WYSIWYG（ProseMirror）编辑面的持续打磨（浮动工具栏、表格 hover 把手等）——建立在已被
   M15 证伪的模型上，暂停投入，等新机制验证完再决定是否重做。
3. "光标在所有场景下都要平滑移动、每次按键同步查一次 Rust 几何"——大幅收窄，自绘机制只
   需覆盖跨块选区高亮，不需要覆盖逐字符移动的动态光标。
4. "长文档编译延迟"作为独立 P2 专项——暂不单开，等 Spike 验证"打字变卡"是否已因新机制
   自然缓解。
5. 继续深挖同类产品——边际收益已经很低，精力转向自己动手做 Spike。
6. 给每种"没有 geometry 的构造"都单独设计一套专属可视化交互——这个想法可以砍掉，但不能
   走向另一个极端"统一走聚焦显源码兜底就够"。准确的处理是 §5A 的三分类：`#set`/`#let`/
   标签复用引用链导航这一个共享 primitive（不需要每种单独设计，但也不是零投入）；注释走
   保真的正确性保证（不是交互设计问题）；只有公式才值得单独投入可视化编辑交互。

### 下一步（按优先级）

1. **Spike 1**：单个段落，聚焦→原生文本框显示源码，失焦→切回渲染态，只验证这一个来回
   观感好不好。这是新方向的地基，过不了这一关，后面都不用做。
2. **Spike 2**：在 Spike 1 基础上加一个相邻段落，验证选区跨块那一刻的提交+切换顺不顺、
   卡不卡。
3. 并行、低成本：核实 Typst 空行分段规则在列表项/表格单元格内是否成立（查 `typst-syntax`
   即可，不用等 Spike 1/2）。
4. **Spike 3**（靠后）：失焦提交 vs 抢跑剥离，对比手感。
5. 独立轨道、可并行：找真实目标用户做"零渲染漂移是否是真痛点"的访谈验证，不阻塞前面的
   技术 spike。

## 11. 术语说明与参考资料

[^wysiwyg]: WYSIWYG 是 What You See Is What You Get 的缩写，也就是所见即所得——编辑时看到
    的样子，就是最终产出的样子。

[^ime]: IME 是 Input Method Editor 的缩写，即输入法编辑器。中文、日文、韩文等语言通过输入
    法把拼音或假名转换成最终文字，这个过程从"组合中（composing）"到"上屏（commit）"——这
    两个词是 M18、M21 里常用的术语。

[^poc]: POC 是 Proof of Concept 的缩写，即概念验证——为验证某个方案是否可行而做的小规模
    原型试验，不代表最终实现，也允许推翻此前的结论。

[^spike]: Spike 是敏捷开发里的说法，指专门为回答一个具体不确定性而写、写完就打算扔掉的
    代码，不是要交付的功能。跟 POC 是近亲，区别在于 Spike 更强调"技术/交互上到底行不行得
    通"，动手前先定死"这次只回答一个问题"，做到刚好能感觉出答案就停，不追求完整、不管边缘
    情况。

[^typora]: Typora 编辑时不显示 Markdown 符号，也没有独立的预览面板。参见
    [Typora - a WYSIWYG markdown editor](https://mallibone.com/post/typora)。

[^typstapp]: typst.app 是 Typst 官方的网页编辑器，默认是源码加预览的分栏形式，可以切换成
    "仅编辑器"或"仅预览"。参见
    [Export and Preview - Typst Documentation](https://typst.app/docs/web-app/export-and-preview/)。

[^synctex]: SyncTeX 是 LaTeX 生态里"正向搜索/反向搜索"的标准机制，能把光标位置和编译出的
    PDF 位置双向对应起来，主流工具大多已经内置。参见
    [SyncTeX - LaTeX Reference](https://tex64.com/learn/editors/synctex)。

[^slashcmd]: Notion 的斜杠命令采用"渐进式呈现"的设计：打字是默认层，`/`、`@`、`[` 逐级
    唤出更复杂的功能。参见
    [Using slash commands - Notion Help](https://www.notion.com/help/guides/using-slash-commands)。

[^texmacs]: GNU TeXmacs 用真实的排版引擎渲染文档，编辑操作直接作用在渲染结果上；对矩阵、
    公式这类结构化内容，它还提供专门的结构化编辑操作。参见
    [GNU TeXMacs: A free, structured, wysiwyg and technical text editor](https://www.texmacs.org/joris/gut/gut.html)。

[^projectional]: 投影式编辑（Projectional editing）指编辑器直接持久化并编辑抽象语法树，
    省去文本和模型之间的往返转换，以 JetBrains MPS 为代表。代价是自由行文的文本编辑体验
    容易变得不自然。参见
    [projectional editor - The MPS Blog](https://blog.jetbrains.com/mps/tag/projectional-editor/)。

[^monaco]: Monaco Editor 是 VS Code 的编辑器内核，它把文本输入和语言服务器这类异步计算
    分开处理：打字走本地同步路径，语言服务的反馈作为异步图层叠加上去。参见
    [VS Code Under The Hood](https://thedeveloperspace.com/vs-code-architecture-guide/)。

[^gdocs-pagination]: 增量/虚拟分页指持续追踪文档里每个元素的位置，先画出页面边界，再把
    精细的排版计算放到背后异步补齐。参见
    [Incremental rendering - Wikipedia](https://en.wikipedia.org/wiki/Incremental_rendering)。

[^mathlive]: MathLive 是一个开源的 JS 数学公式编辑器，支持可视化编辑，同时底层和类 LaTeX
    源码保持双向同步。参见
    [List of web based math editors](https://github.com/mathjax/MathJax-docs/wiki/List-of-web-based-math-editors)。

[^citepicker]: Overleaf 的 Insert Citation 按钮和 Google Docs 的 Cross Reference 插件，都
    是唤出一个可搜索的列表，选中目标之后自动维护编号。参见
    [Adding citations and references - Overleaf docs](https://docs.overleaf.com/citing-and-references/adding-citations-and-references)。

[^typst-svg-a11y]: Typst 官方文档说明，`typst-svg` 为了保证跨设备的一致性，把字形转成路径
    而不是文字节点，代价是文本没法被复制或读屏，官方建议需要可访问性时改导出 PDF 或 HTML。
    参见 [SVG - Typst Documentation](https://typst.app/docs/reference/svg/)。

[^pdfjs-textlayer]: PDF.js 采用分层架构：canvas 层输出像素，上面叠加一层不可见的 Text
    Layer，提供原生的选中、搜索和无障碍能力。参见
    [How to Enable Text Selection in PDF.JS](https://usefulangle.com/post/90/javascript-pdfjs-enable-text-layer)。

[^underleaf]: Underleaf 是一个已上线的 Typst 可视化编辑产品，宣称使用"official Typst
    compiler...via WebAssembly"，编辑区和源码之间是切换（flip to source）关系，不是聚焦
    即显源码。实测发现编辑区渲染和导出 PDF 有实质差异，write 模式下列表项无法通过"+"添加，
    行首 `# ` 会被错误渲染成一级标题。参见
    [Visual Typst Editor — Write Typst Like Google Docs](https://www.underleaf.ai/visual-typst-editor)。

[^tyx]: TyX 定位是仿 LyX 的 Typst 可视化编辑器，基于 Lexical 和 Tauri 构建，用真实的
    Typst 编译器（通过 typst.ts）渲染。项目明确处于早期阶段，"breaking changes are
    introduced frequently"；目前相对完整的能力是用 MathLive 做公式可视化编辑（暂时仍是
    LaTeX 语法），Typst 语法导入"许多特性还导入不正确"。参见
    [TyX Documentation](https://docs.tyx-editor.com/en/latest/) 与
    [GitHub - tyx-editor/TyX](https://github.com/tyx-editor/TyX)。

[^typstudio]: Typstudio 是一个 Typst 桌面编辑器，架构是源码 + 实时预览的分栏（不是可视化
    编辑、不隐藏语法），后端用真实的 Typst 编译器。项目已停止维护，作者原话是"has not had
    time to actively maintain this project for the last year"，并推荐 Tinymist 作为替代。
    参见 [GitHub - Cubxity/typstudio](https://github.com/Cubxity/typstudio)。

[^katvan]: Katvan 是一个真实开发者为"希伯来语+数学+英文混排"这个具体需求做的 Typst 编辑
    器，解法是把双向文本相关的代码编辑器体验做好，不是做可视化编辑——提示 CJK/RTL 这类
    混排痛点，不一定要靠 WYSIWYG 解决。参见 [GitHub - IgKh/katvan](https://github.com/IgKh/katvan)。

[^remo-forum]: Typst 官方论坛上一个 WYSIWYG word processor 的展示帖，作者是为了帮同事
    摆脱源码而做的，社区反应正面，但作者明确承认"Typst 支持很广泛的编程语言特性，用纯
    WYSIWYG 的方式呈现这些特性，可能很棘手甚至不可能"。参见
    [Typst WYSIWYG Word Processor - Showcase](https://forum.typst.app/t/typst-wysiwyg-word-processor/9109)。

[^typst-gui-discussion]: Typst 官方仓库一条关于"是否需要 GUI"的讨论，正反双方都有真实
    用户声音：公式输入体验、写作心流被打断、双屏需求是真实抱怨；反对声音认为可编程性会被
    牺牲、GUI 不等于好体验。参见
    [good UX requires a GUI · typst/typst · Discussion #2858](https://github.com/typst/typst/discussions/2858)。

[^typst-cjk-issue]: Typst 官方仓库一条至今未关闭的 issue，讨论 CJK 断行规则和两端对齐时
    标点的处理，说明这是引擎层面的已知缺口，不是编辑器能解决的。参见
    [Better CJK support · Issue #276 · typst/typst](https://github.com/typst/typst/issues/276)。

[^overleaf-richtext]: Overleaf 的 Rich Text 模式，官方定位是服务"部分合著者只会 LaTeX、
    部分只想用类 Word 界面"这种跨技能协作场景；也有自定义宏在该模式下渲染不出来的已知
    问题。参见
    [Rich Text Mode · Issue #349 · overleaf/overleaf](https://github.com/overleaf/overleaf/issues/349)。
